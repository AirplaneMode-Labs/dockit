# Benchmarks: raw results

Every figure dockit quotes about speed or memory is a row in a file here, with the date, the commit and the machine on the row. The tables in the [README](../../README.md#benchmarks) and the dated status line of the page are generated from
these files (`node scripts/bench-readme.mjs`, `node scripts/status-line.mjs`), the page links to this folder from its footer, and `test/benchmarks-index.test.ts` fails when a file or folder here is missing from the index below or the
index names one that does not exist. Owner decision, 20 Nov 2026: every repository's raw benchmark results live under `docs/benchmarks/` with an index like this one.

**Standing lines.**

- Every Mac figure is from one machine, an Apple M5 Pro with 48 GB. It is a development machine, not the target.
- The Windows files are emulated: one GitHub-hosted Windows Server VM with 4 vCPU and 16 GB RAM, with the pwsh, node and Chrome process tree under a job commit limit. They are not a laptop.
- Nothing is measured on an 8 GB laptop. Every row of every CSV reads `not measured on 8 GB` in its `laptop_8gb` column, and the 8 GB Windows done-when stays NOT met (owner runbook step 5).

How to read a row:

- `date` is the start of the run's session in UTC, repeated on every row of that run. `commit` is the dockit commit that was built and measured, 12 hexadecimal digits, never `-dirty`. The sibling builds it was assembled from are the commits in
  `deps.lock.json` at that commit (`git show <commit>:deps.lock.json`).
- **current**: the Sprint 7 measurement that the README tables and the status line are generated from. **historical baseline**: an earlier measurement kept because a README table rests on it (the before rows of the Sprint 6 memory
  work). **historical**: an earlier run that is in no README figure.
- Timings are not deterministic. Another machine, or this one on another day, gives other milliseconds, and a re-run writes rows of its own. `npm run bench:e2e` writes `docs/benchmarks/e2e.csv` and `e2e-questions.csv` by default, so to check a
  re-run without replacing the committed files, point `DOCKIT_BENCH_CSV` and `DOCKIT_BENCH_Q_CSV` somewhere else.

## Reproduce

**R1: the Mac files.** From a clone of dockit at the commit named in the row, on an Apple Silicon Mac with installed Google Chrome, Node 22.12 or newer and the Rust 1.98 toolchain with the `wasm32-unknown-unknown` target (the README, "Install" and "Usage"):

```sh
npm ci --ignore-scripts
node scripts/assemble-deps.mjs --checkouts <dir>   # clean checkouts of the four siblings at the commits of deps.lock.json, as pages.yml does (--siblings .. takes clones side by side instead)
npm run build
DOCKIT_BENCH_CSV=<out>/e2e.csv DOCKIT_BENCH_Q_CSV=<out>/e2e-questions.csv npm run bench:e2e   # 5 runs in one Chrome session, then 1 after a Chrome restart
```

Without the two variables it writes `docs/benchmarks/e2e.csv` and `e2e-questions.csv` in the clone. The row columns are those of the commit that was checked out. Wi-Fi off at the line `cache phase done` is how the owner's 8 GB run is made (the README, "Run the end-to-end benchmark").

**R2: the emulated Windows files.** The manual `bench-windows` workflow takes no input and never runs on a push; dispatching it is the main session's or the owner's step, never a team agent's. It runs at the tip of the ref it is dispatched from:

```sh
gh workflow run bench-windows.yml --repo AirplaneMode-Labs/dockit
gh run list --repo AirplaneMode-Labs/dockit --workflow bench-windows.yml
gh run download <run-id> --repo AirplaneMode-Labs/dockit   # one artefact per leg: bench-windows-<cap>-<sha>, kept 7 days
```

Each leg's `bench-out/` holds the two CSVs, `env.txt`, `job-summary.json` and the logs. The workflow's own step fills the job columns (`node scripts/bench-emulated-merge.mjs --csv <leg's e2e-emulated-win-vm.csv> --summary <leg's job-summary.json>`); how the third run's legs were joined into the two committed
files, with the control leg's marker row, is in `scripts/win/README.md` ("How the third run was imported"). A dispatch at a later commit is a new run with its own rows and its own folder; it does not replay `f6a71cab4ab1`.

## How the README is held to these files

- `node scripts/bench-readme.mjs --check` fails unless every table of the README Benchmarks section, and the inline figures marked `<!--fig:...-->` in the Limitations, are exactly what the CSVs here produce; `node scripts/status-line.mjs --check` does the same for
  the status line of the page.
- `test/bench-readme.test.ts`, `test/bench-emulated-columns.test.ts` and `test/bench-emulated-run2.test.ts` pin the columns, the history files and every evidence cell of every emulated row against the committed summaries.
- `test/benchmarks-index.test.ts` pins this page: every file and folder here is in the tables above, the tables name nothing that is absent, the dates, commits, machines and row counts of the CSVs equal the rows, the runner and the limit of each leg equal its `env.txt` and
  `job-summary.json`, the standing lines are present, and every figure in the next section is still quoted where this page says it is quoted and still carries its mark.

### Quoted figures that are not benchmark rows

- **Sizes of build outputs**, printed by the build and not timings or memory: the model bundle "about 754 MiB, at most 900 MiB" (built by runtime's `scripts/bundle-models.mjs`, which enforces the cap), the "roughly 800 MB" Pages artefact (`pages.yml` prints `dist total: <bytes>` and refuses
  more than 1,000,000,000 bytes) and the 1,426,069,098 bytes of the Qwen3-1.7B 4-bit graph (a size pinned in runtime). The `storage_usage_bytes` column of `e2e.csv` is what the browser reported after the run.
- **Limits, thresholds and scenario parameters**: the 20 MiB file limit, 300 pages, the 60 second pdf timeout, the stream limits of pagetriage (32, 256, 64 and 512 MiB), the 4 GB memory line, the 1.5 second load retry (`LOAD_RETRY_PAUSE_MS`), the 10 second fail-fast
  threshold, the 12-minute and 80-minute stops of a leg, the targets of TD-66 (5,120 MiB and 12,500 ms), and the probe's 64 MiB commit and its commit of the limit plus 256 MiB.
- **Test timings** in `CHANGELOG.md` and `test/helpers/timeouts.ts` (the pdf.js fixture tests: 5 673 ms on a windows-latest runner against 115 ms locally, from CI run 44325772916): they explain a timeout, are not benchmark rows, and their raw log is the CI run's, which GitHub keeps for a limited time.
- **Counts of a proof**, not of a benchmark: "24 of 36", "0 requests after offline" and the like are computed from the CSVs; "no request left the page" is also asserted by `npm run test:e2e`.

`runtime` quotes "about 1.8 s" for the next load of the 0.6B answer model after an unload (TD-64) and attributes it to dockit (its `README.md` and `docs/memory-options.md`). dockit does not quote it, no row here holds it, and runtime marks it "raw data not kept" too. The only reload time
dockit quotes is the 2.3 seconds in the first row of the table above, with the same mark.
